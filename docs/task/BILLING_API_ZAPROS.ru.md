## 0. Просьба подтвердить наши выводы

Три пункта, где нам, возможно, **не нужна доработка** — достаточно подтверждения.

### 0.1. Дата начала текущего тарифа — берём из `/tariff/connected`

При опросе API метод `/tariff/connected` вернул:

```json
{"tariffs": [{
  "tariff_id":    "1197",
  "tariff_name":  "Smart 300 - 355 000 сум",
  "date_begin":   "2026-08-10 16:34:27",
  "date_end":     null,
  "tariff_isoff": "0"
}]}
```

`tariff_id` совпал с `curr_tariff_id` из `/abonent/info`.

**Правильно ли мы понимаем, что `date_begin` — это дата вступления в силу
действующего тарифа?** Если да, отдельное поле `current_tariff_start_date`
в `/abonent/info` **не требуется** — мы уже берём его отсюда, сопоставляя по
`tariff_id`.

Дополнительно просим уточнить:

- метод возвращает **только действующие** записи или также завершённые?
- в каких случаях `date_end` не `null`?
- что означает `tariff_isoff = 1`?

### 0.2. Дата следующего списания — поле не требуется

Правило нам подтвердили: **расчётный период заканчивается в тот же день месяца,
в который тариф был подключён.** Дату начала мы получаем из `date_begin`
(п. 0.1), поэтому дату списания кабинет вычисляет сам:

```
подключён 13.08.2026                    →  списание 13.09.2026
подключён 10.06.2026, сегодня 13.08     →  списание 10.09.2026
```

Первое списание — через месяц после подключения (в день подключения списания
нет). **Поле `next_charge_date` в `/abonent/info` не требуется.**

Просим уточнить **один** случай: если тариф подключён **31-го**, в каком числе
происходит списание в феврале, апреле и других коротких месяцах? Мы исходим из
того, что дата прижимается к последнему дню месяца (28/29/30), а не переносится
на 1-е число следующего. Если это не так — сообщите, поправим.

### 0.3. Номер договора уже есть в БД

Метод `/device/newoneclick` возвращает в курсоре колонку `CONTRACT_NUMBER`.
То есть источник данных существует, и добавление `contract_number` в
`/abonent/info` не требует нового источника — только вывода уже имеющегося поля.

## 1. Доработки, которые нужны

Приоритет **0** — блокирует функциональность, **1** — ухудшает, **2** — желательно.

| П | Метод | Что добавить | Тип |
|---|---|---|---|
| **0** | `/tariff/history` | **новый метод** — история смены тарифа | `history[]`: `change_date`, `old_tariff_name`, `old_tariff_cost`, `new_tariff_name`, `new_tariff_cost`, `changed_by` |
| **0** | `/abonent/info` | `curr_tariff_cost` — стоимость действующего тарифа | int, тийин |
| 1 | `/abonent/info` | `contract_number` (см. п. 0.3) | string |
| 1 | `/abonent/info` | `next_tariff_name`, `next_tariff_cost` | string \| null · int \| null |
| 1 | `/acct/payments` | `payment_status_code` — машинный код статуса | `paid` \| `pending` \| `failed` \| `cancelled` |
| 2 | `/traffic/detail`, `/acct/payments` | параметры `date_from`, `date_to` | `Y-m-d`, необязательные, включительно |
| 2 | `/loyalty/info` | **новый метод** — бонусы, уровень, привилегии | `bonus_balance` int · `tier` string \| null · `privileges[]{name, description}` |

Пояснения:

**`/tariff/history`** — `/tariff/connected` возвращает только действующий тариф
(одна запись), истории в нём нет. Без истории кабинет не может показать
абоненту, когда и на что он менялся.

**`curr_tariff_cost`** — сейчас мы пытаемся найти действующий тариф в списке
`/tariff/available` по `tariff_id`, но гарантии, что он там есть, нет: список
содержит доступные для подключения планы, а не текущий.

**`payment_status_code`** — сейчас `payment_status` приходит переведённым по
`lang` («оплачено» / «to'langan»), поэтому кабинет вынужден распознавать статус
по тексту, и любое изменение формулировки ломает отображение. Альтернатива
новому полю — полный список возможных значений (см. п. 2).

**`date_from` / `date_to`** — сейчас оба метода принимают только один месяц. Мы
проверили: при передаче диапазона без месяца возвращается ошибка `115`, а вместе
с месяцем диапазон молча игнорируется. Отчёт за 12 месяцев = 12 HTTP-запросов.

**`/loyalty/info`** — если программа лояльности живёт в отдельном сервисе,
метода не нужно: достаточно **URL**, на который мы поставим ссылку.

## 2. Вопросы, на которые достаточно ответа (без доработки)

Три значения, которые приходят из БД «как есть», — по коду шлюза их смысл не
определяется.

| Поле | Метод | Источник | Вопрос |
|---|---|---|---|
| `abonType` | `/identify` | `ABON_TYPE` | Какое именно числовое значение соответствует юридическому лицу, а какое физическому? Мы знаем, что `0` — временный и `1` — разовый, а постоянный абонент разделён на два кода, но не знаем, какой из них какой |

| `readonly` | `/device/list` | `DEVICE_READONLY` | Какие значения и что означают |
| `connect_cost` | `/device/list` | `DeviceList` → `oSrvCost` | Что означает `-1`: «подключение недоступно» или «цена не задана»? В каких единицах приходит значение? |

**`phone`** в `/abonent/info` приходит как `"712070807,,"`. Мы понимаем, что это
список номеров через запятую и шлюз его не обрабатывает. Просим подтвердить
формат и пояснить, что означают пустые элементы в конце.

## 4. Отдельно: локализация сообщений об ошибках

В справочнике сообщений блоки `uz` и `en` — точные копии русского. То есть
`errMsg` возвращается на русском при любом значении `lang`.

Это не блокирует работу: кабинет показывает собственные переводы по коду ошибки.
Но если планируется отдавать `errMsg` напрямую другим потребителям API —
блоки стоит заполнить.
